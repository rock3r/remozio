# Permanent replay capacity and account continuation

Refs #1061. Related: #1005, #1059, #1065. Source baseline: `9b7155e78f1494b6d02322ea84a0206e45e16985`. Part A covers capacity diagnostics. Part B records the agreed guarantee and the cutover requirements. Part B implementation is deferred and needs a separate review.

## Part A. Show the limit and make a full account diagnosable

The installed cap is **1,000,000 consumed request IDs** and **1,000,000 command submissions with their paired nonces** per account. Each reservation consumes one submission slot. The nonce is a second lookup key for the same slot. The live receipt count is a separate limit. Retirement can free receipt detail, while permanent counts continue to accumulate. The two-million-entry fixtures from #1065 measured scale and did not raise the installed cap.

### Where the user sees it

- **Mac Unified Log.** Use the existing Authority logging path under `dev.sebastiano.remozio.macos.authority`, with a dedicated `replay-capacity` category. A support technician can find the events in Console. Emit a notice at 80% and 95%, and an error at the cap. Use separate counters for `consumed_requests` and `command_submissions`. Each event contains a fixed reason, current count, limit, and band. Leave account IDs, request IDs, nonces, keys, payloads, and paths out of the event.
- **Mac command caller.** When it receives a verified `capacityExceeded` admission result, show “Approval capacity reached. See Remozio diagnostics.” Keep the existing exit status and no-retry behavior. That result can also signal temporary capacity. The text deliberately covers both. The Authority log identifies permanent exhaustion after verifying the exact counter.
- **Setup, Paired Phones, and the phone.** Use the log for this slice. A banner would need a trusted, account-scoped status source that these screens do not currently carry. If Console proves insufficient, propose one account-level capacity row in Setup through an existing verified status read once available. Keep phone frames unchanged. The signed decision refusal frame has no capacity reason, so it cannot carry a precise new phone error in this slice.

### Observation and refusal

1. Read the scoped `PermanentReplayCounters` in the existing verified startup read and in the existing validated admission or consumption transaction. Use the exact bounds enforced by each guard. Do not add a full journal scan or a second checkpoint read to successful hot paths. Capture the current reason at the guard to distinguish exhausted permanent keys from live receipts or transient in-memory limits.
2. Prepare an observation in the transaction and emit it only after its outcome is proved. A threshold crossing from an increment needs the durable commit and checkpoint. A rejection needs the existing proved no-write or rollback path. A storage or integrity failure has its own outcome. It does not provide a capacity observation.
3. Compare integer counts with inclusive 80%, 95%, and 100% boundaries. At steady state, report each newly reached band once per counter per Authority lifetime. On startup, report only the highest band already reached. Rate-limit repeated refusals from the same full counter. Suppression is memory-only and resets on verified startup.
4. On a full command set, retain the existing authenticated `capacityExceeded` result where supported. On a full consumed-request set, keep the current fail-closed decision path and report the stable local diagnostic. Do not report success or retry from the diagnostic. A format 19 journal cannot supply permanent counts. Report no permanent band for it and leave its existing limits in place.

No changes to SQLite format, stored rows, signatures, wire types, or the numerical limit. Relevant seams are `InstalledAuthorityCommandRegistration.swift:163–185`, `PermanentReplayCounters.swift:65–87`, `ConsumptionJournalTables.swift:69–119`, `CommandSubmissionReplayTables.swift:72–116`, `ApprovalRequestCoordinator.swift:605–648,796–821`, and `CommandFrontendMain.swift:279–290`.

## Part B. Design a successor account scope

A full account needs an operator-authorized succession workflow. Recommend a fresh account ID, a new journal and continuity scope, explicit routing to the new account, and fresh enrollment. Re-pair within the same account leaves the same quota keys. An audit recovery epoch is also insufficient on its own. The current `ChannelScope` binds Mac, account, phone and enrollment epoch, and `DecisionVerifier` checks the retained request and challenge in addition to scope.

### Proof and durability requirements

- **Bind authorization to the successor.** Close old admission and resolve or fence in-flight work before changing the route. The old scope may serve authorized historical reads. It cannot admit new work or accept old authorizations. Do not move an old active request, signed decision, command grant, or execution permit. A new pairing and caller capture must bind to the successor scope. Reject former-scope proofs even if presented on a current channel. Preserve revocation, policy, and audit history. A fresh account does not reactivate a retired phone.
- **Keep replay refusal exact within each account.** A successor requires new authorization and keeps its own permanent replay sets. Keep the predecessor readable under its verified final checkpoint. The successor does not look up every old replay key. It checks the bounded drain set described below before it reserves a new submission. The [guarantee decision](https://github.com/rock3r/remozio/issues/1061#issuecomment-7236889635) and [drain addendum](https://github.com/rock3r/remozio/issues/1061#issuecomment-7236892746) define this boundary.
- **Recover the cutover.** Review how the protected account registry, the old drain and the new store share a durable transition record. That record must bind both store identities and the predecessor's final checkpoint. Reopening requires the successor's validated state and routing plus a monotonic indication that old admission cannot reopen. Exercise restart after drain, after writing the successor, before and after routing changes, and before admission opens. A partial transfer cannot activate both journals. An older binary or stale snapshot must fail closed through the supported reader floor. Keep the predecessor readable so the user can still inspect prior audit and state.
- **Check routing durability and backup boundaries.** Treat admission open before durable routing as an invalid state. Inject a crash at that boundary and prove that startup fences both routes until the transition is reconciled. Test restoring an older registry alone while the old fence, successor checkpoint, or committed routing remains current. Startup must detect the mismatch and refuse to reopen old admission. A complete, internally consistent rollback of the registry, both scopes, their floors and other protected state cannot be detected from those restored stores. That is the existing [whole-Mac backup boundary](../docs/design-decisions.md#whole-mac-backup-rollback). No independent witness is assumed.
- **Define the user action.** Document what is carried into the new account, which phones need fresh enrollment, and how the old history is opened. Review caller and Gateway scope ownership and the order of revocation and replacement. This design is not a reset button or a supported procedure today.

**Decided guarantee.** Cross-account replay prevention covers authorization proofs. Exact replay membership applies within each account. A raw value reused across accounts can ask for new approval, subject to the drain exclusion below. No existing integration is assumed to promise cross-account idempotency. An integration that makes that promise needs its own durable scope.

### Lost terminal result and a retry across the cutover

The stock caller does not resubmit after a missing admission or terminal reply. Before it exposes a submission it may retry endpoint lookup and handshake. After exposure it may make a fresh submission only on a verified busy refusal with an allowed retry class. That branch generates a fresh ID and nonce and uses the configured bounded readiness backoff. A lost or uncertain result does not enter that branch. After admission, the CLI stays on its single execution session. If reception fails it closes the session, restores local terminal state, and returns the error. There is no timer that resends the submission. Starting a new CLI invocation creates new values. A custom caller can choose to reuse previous values. The Authority may retry the delivery of the exact terminal bytes after a known zero-progress send. That operation cannot retry execution.

A custom retry that survives the cutover can obtain a new request, never the old command grant. Root creates a new request ID and challenge. The successor's decision check requires its own account, enrolled phone, request digest and challenge. The capture starts queued. Dispatch requires an authorized live entry and a durably consumed `execute` decision bound to that entry. It transfers the exact current execution resources only once. If the user explicitly approves the new request and the old command had already run, the command can run a second time. The system does not claim exactly-once execution across accounts. It never executes from the predecessor's decision. A stock CLI rerun with fresh keys is outside exact-key retry suppression and still needs a fresh decision.

### Bound the retry exclusion at the drain

- Define an acknowledged outcome as a verified receipt from the same caller session for the exact terminal-result binding. Today's `outputDrained` acknowledgment concerns output bytes. A successful enqueue of terminal bytes also does not prove caller receipt. The cutover design needs an authenticated terminal acknowledgment or a conservative way to retain all unconfirmed attempts in the owned drain cohort. Treat crash, timeout, missing proof, and lost acknowledgment as unconfirmed. Do not infer acknowledgment from process exit or a successful send.
- Give the protected predecessor owner a fixed maximum for the cohort. Establish a tracked attempt before admitting work covered by the cutover. Keep its verified submission ID and nonce until terminal acknowledgment is durable or a no-execution outcome is proved. Preserve the uncertainty record across restart. The live request limit is not a proof of this maximum: terminal attempts without acknowledgment can outlive the live owner. Define how older clients enter the drain and when missing evidence requires holding the cutover closed. If the owner cannot account for the whole required cohort within the supported bound, do not cut over by dropping entries.
- Close predecessor admission and settle its execution and delivery owners before freezing the cohort. Bind the canonical pairs, their count, the predecessor final checkpoint digest, and both account identities into the durable transition record. Preserve the record until the successor scope retires. After verifying the record, check the submitted ID **or** nonce against the carried keys before the successor's reservation write. A match refuses the invocation without creating a request. An unrelated new key still uses the existing same-account replay guard. The record carries keys and proof of scope. It carries no terminal result, pending approval, or permission to execute.
- Exercise loss before terminal receipt, receipt with lost acknowledgment, matching ID with a different nonce, matching nonce with a different ID, crash after recording the drain, and replay of an earlier transition. Verify that a successful exact match never creates a request and that a retry with unrelated keys can execute only after a new decision.


### Relationship to #1059

A format 19 journal with a recorded gap cannot prove a complete lifetime set. `CheckpointedJournal.installPermanentReplay` skips it and `PermanentReplayJournal.seed` independently refuses it. A successor design that depends on complete historical raw membership does not solve this case. Never label a seed of the surviving rows complete. Preserve all available predecessor evidence.

Under the [#1059 decision](https://github.com/rock3r/remozio/issues/1059#issuecomment-7236889817), a legacy account with an authenticated finalized gap can move into the new scope without a claim of complete pre-gap membership. Old-scope proofs remain fenced. That does not install format 20 in the old account. Unresolved recovery still blocks the transition until the old state can be verified. A fresh prefix inside the existing random ID width cannot prove disjointness from unknown old raw IDs. The drain set comes from verified cutover ownership and current unconfirmed attempts. It makes no claim about missing pre-gap keys. Keep the existing migration guard for the old format 19 store.

### Review and evidence before implementation

Saturn should review raw ID and nonce reuse across scopes, predecessor corruption, missing history, stale routing, rollback, restart, and how the plan preserves already-committed effects. Measure drain and successor startup costs at the proposed cohort bound. Verify that carried values refuse before admission, and that other repeated values require a new decision, cannot select an old result, and still trigger exact duplicate refusal within the successor. Start with the permanent replay loss/restart fixtures in `CheckpointedJournalTests` and `ApprovalRequestCoordinatorTests`, and reuse the protected pairing replacement fixtures for enrollment and routing. Add a small signed test matrix for old-scope proofs and re-enveloped raw keys. Validate installed account transition separately.
