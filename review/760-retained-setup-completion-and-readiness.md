# #760 retained Setup completion and readiness

Revised design for review. Base `76dd4cc82b15b20b52a92af081fcd8688f0a5928`. [#760](https://github.com/rock3r/remozio/issues/760) · [#960](https://github.com/rock3r/remozio/issues/960) · [#603](https://github.com/rock3r/remozio/issues/603)

## Entry and ownership

C02 begins after the retained runtime publication and import acknowledgement, native activation, and verified job registration. The authenticated Setup invocation selects the target account from the current caller binding, installed inventory and durable plan. It retains the accepted rights and the selected owner through cleanup. The target holds the activation plan v6, the registered jobs and the recorded startup policy. Treat `jobsRegistered` as a durable result of registration. Verify the actual jobs and live peers separately.

Setup owns the machine rows and release placement. The retained target Authority job owns the journal and continuity pair and executes the policy write. The same authenticated connection provides health and accepts the one-use floor command. The job keeps both pair leases through observation, commit and receipt. Setup closes the machine connection before any RPC. Use the existing Root Setup identity, owner-bound operation, release placement custody and `UpdateOrdinaryAdmissionLease` to exclude concurrent machine updates. Keep the target command and pairing admission closed through settlement. Resolve the current Authority from the verified caller. Its separate read-only lease and the target job's startup lease still need the #725 live check.

A native registration producer for the retained plan and authenticated stage-specific health are prerequisites. The generic activation writers operate on the ordinary plan and the stable transaction gate rejects their use on this store. The existing retained health service label and transcript readers provide the naming and verification contracts. A production listener, verified job identity and exact v6 registration must all be present before C02 is reachable. An owned fixture can set up a database frame to exercise the storage logic. Its proof type cannot enter native dispatch.

## Durable operations

Keep historical record readers. Add a completion record version for the incarnation-bound writer on schema 29. The current v1 writing record carries no incarnation evidence. Each machine write uses one private, process/thread-bound store authorization in the existing stable-store transaction dispatcher. One connection holds the exclusive machine storage lease for each synchronous transaction. Store captures use the active transaction's narrow frame loan. Invalidate it on return, and refuse nesting, cross-thread use or another writer. Close the machine connection before asynchronous health, service actions or the separate target pair write.

Use a bounded row count and the existing codec size limits. Compare an exact existing row after validating the same frame. A matching durable result is readback. Refuse unrelated rows, conflicting IDs or replacement of a historical readiness verdict. If future requirements allow a new promotion for an account already carrying a readiness record, specify its exact replacement and archival contract separately before adding an update path.

For readiness, construct the record only from the native client's one-use proof. Use a new challenge with a bounded deadline. Verify the root/account-specific job, code identity and key, and the Transport job, execution UID, code identity and key. Bind both peers to the exact candidate, activation, inventory, recorded policy and checkpoint and published promotion. Transport signs its own reply over the child challenge bound to Authority's challenge, candidate and publication. Authority signs the joint transcript that includes the Transport request and reply digest. Setup verifies each signature independently against the corresponding authenticated peer and key. A reconnect or process replacement invalidates the exchange even when it uses the same signing key. Archived transcript verification has no native peer-liveness authority. A stored v1 record preserves the verified transcript. Require current health again at any later admission boundary. Keep keys, raw transcripts and account identifiers out of shared diagnostics.

## Schema 29 and compatibility

A machine that has run retained maintenance can already have schema 29 with the completion, promotion and readiness tables present and empty. On 29 all three producers modify data in their own existing table. Preserve `user_version`, the window table and every window row, the full catalog, and unrelated rows byte-for-byte. An earlier window provides no writer authority for these operations. Verify the exact settled maintenance state and reject conflicting active or unresolved work.

Audit schema gates at each level. This includes the format requirements and proposal factories, stable and catalog capture, snapshot retention and transition comparators, native scope, private authorization and primitive, and the transaction dispatcher. The reader-side acceptance of 29 does not establish a writer contract. Keep ordinary account, inventory, update and window writer guards narrow. Include catalog and protected-row comparison even when schema stays constant.

All new producer paths require a verified schema 29 catalog. A missing table, unexpected schema or role/format mismatch refuses before mutation. Keep the historical readers and the existing 28→29 window owner. Historical producer migrations 25→26→27→28 belong in a separate issue and require a reachable installation that needs them.

Update signed manifest assertions together with each reachable path. Require Authority and Setup readers for the actual schema and records carried by the installation. Declare machine table writers on Setup and journal policy authority on the role that performs that write. Reconcile the current promotion proposal's legacy role/version lists with that concrete producer matrix. Require the new completion version only for the new writer and its consumers. Preserve canonical v1 archive/read support. Review all readers and embedded completion projections, including promotion and manifest checks, before declaring v2. If a nested envelope needs a new version, stage that reader closure before publishing the producer. Check declarations and compatible reader floors before opening the write transaction.

## Rechecks at each boundary

1. Resolve the peer UID, current authority, target owner, directory identity and installed code from native evidence. Verify candidate signatures, placement, the stable seal and admission boundary. Pin the activation plan, inventory, registered job identities, exact source or promoted files, and both sides of the relevant pair. Acquire scoped custody and prove the same frame again.
2. Perform asynchronous health with the machine connection closed. Bind the proposed marker to the authenticated job and attempt. Inside the machine transaction compare a fresh frame with the challenge frame, the selected row with exact expected bytes, and the full protected digest. After mutation verify the expected row, recheck the same owner and pinned observation before COMMIT, and read back the durable marker before dispatch. A transaction callback uses its synchronous borrowed frame and checks the live local session fence. Schedule peer RPCs outside the machine transaction.
3. The Authority handler checks the kernel peer and the exact connection that issued health. It serializes health and mutation on the owned pair, validates the durable marker through a bounded, fresh machine read, and consumes the one-use command before applying a changed policy. Validate source and bound operands before and inside the checkpointed write. Setup holds no machine transaction while awaiting that RPC. The job retains immutable proof and exclusive leases through the receipt. Failure or connection loss retires the capability. A delayed response alone grants no second write.
4. To record a receipt or readiness row, take a bounded pinned observation from the same owned pair scope rather than asking Setup to open competing exclusive leases. Recheck scope and pair around the machine read and CAS. The job keeps the observed pair and closed admission stable until the owner settles; the Setup transaction uses the pinned observation and checks the peer lifetime. On loss after commit retire the local owner and reconcile from a fresh authenticated scope. In readiness also verify the six selected files and the exact published intent immediately around insertion. Keep the health verdict historical unless checked fresh at an admission boundary.
5. For re-arm, store the original authenticated process identity in the v2 writing marker. Use a kernel audit-token-derived process identity (PID and PID version, with a boot identity), bound to the account, registered job, signed release and verified connection. The connection credential triple in `XPCPeerPolicy.swift:53–71` alone is insufficient. Use a native identity observation bound to the live connection and a guarded exit observation. The existing audit-token sampling in `CommandAncestryObservation.swift:56–86` is a precedent, not a retained proof factory. Prove the exact old process exited, or prove its PID was reused by a different kernel PID version in the same boot. An unverified new hello, disconnect, timeout, differing UID or failed lookup cannot establish exit. Require positive native proof for the previous boot as well, or leave the re-arm unavailable. Store only the protected identity fields needed for comparison and omit them from logs.
6. Keep the machine frame cache scoped to a single connection and transaction. #960 uses the real registered fixture from C02, commits on a second connection between the two reads of `readFresh`, verifies that commit, and expects `staleRevision` on the second read.

## Interrupted execution

| Last established state | Restart behavior |
| --- | --- |
| No committed machine transaction | Roll back the pending row changes. Resume from a fresh verified frame. |
| Exact committed `.prepared` | Read it back in a fresh scope. Revalidate all operands before starting the next transaction. |
| `.writing` with uncertain acknowledgement or lost permit | Retire the old session and read the pair under the new authenticated Authority's exclusive custody. If the pair is exactly the startup policy, role revisions and checkpoint **and** native evidence proves that the bound incarnation is gone, Setup can CAS `.writing(rev n)` to `.writing(rev n+1)` with the new authenticated incarnation, same ID and immutable operands. Recheck the proof and unchanged pair under pinned custody. Read back the new revision, then permit one command on the new health connection. The old revision stays invalid. A historical v1 marker, ambiguous incarnation, changed pair or partial pair goes to explicit owner recovery unless the exact final pair can be recorded. |
| `.writing` with proven exact target pair | Validate the existing record's checkpoint, generations, role revisions, digests and unchanged journal head. Record the result with one exact machine CAS. The equal-policy case can record the unchanged exact scope as a no-op receipt. |
| `.recorded` or file promotion interrupted | Verify the actual recorded pair and the same publication intent. Treat already-selected bytes as completed work. Stop on foreign bytes or an uncertain file identity. |
| Readiness commit outcome uncertain | Close the writer and read the actual row in a fresh scope. Return only the exact existing historical result after proof checks. If absent, repeat the read-only native exchange with a new challenge and recheck before a new insert. Fresh health and the separate owner govern any later reopening. |

Use the store's existing poisoned-connection behavior for unknown COMMIT, failed rollback, corrupt records and late custody loss. A definite pre-transaction refusal must leave a valid connection available where the transaction contract permits it. Preserve the primary error through cleanup. The owner releases its leases after actual close or join.

A project of roughly **10–15 focused PRs**. Count the listener work once with the health block. Each slice follows its prerequisite and keeps native capabilities unreachable until the required producer is present.

| 13–15 | Isolated promotion on 29, independently verified joint readiness on 29, and final admitted composition and installed handoff. | 9–11 and native health. Treat #960 as a proof gate for promotion. |

Owned test coverage per slice includes actual schema 29 database writes on an empty and populated 29 catalog. Check schema 25–28 refusal through the new entry, schema and row digest preservation, missing or corrupt declarations before BEGIN, duplicate and stale CAS, separate-connection drift and writer exclusions. Inject failures before BEGIN, inside the body, before COMMIT, during COMMIT, after commit and between all durable phases. Check the actual persisted rows, lease retirement, fresh reopen and result classification. Test exact v2 re-arm, historical v1 refusal, same PID reused with a different version, no death witness, still-live old job, stale old-revision command, lookup and permission errors, and second lost response after re-arm.

Use the existing scoped ATC workflow for focused and full gates with Toni's approved test selection and budget. Separately verify live Root and Transport jobs and signing, the busy case from #725, actual installed pair mutation, and restart/readiness on the owner-approved Mac.
