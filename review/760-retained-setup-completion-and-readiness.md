## Entry and ownership

C02 begins after the retained runtime publication and import acknowledgement, native activation, and verified job registration. The authenticated Setup invocation selects the target account from the current caller binding, installed inventory and durable plan. It retains the accepted rights and the selected owner through cleanup. The target holds the activation plan v6, the registered jobs and the recorded startup policy. Treat `jobsRegistered` as a durable result of registration. Verify the actual jobs and live peers separately.

Setup owns the machine rows and the protected placement. The target Authority policy writer owns the journal and continuity pair. Use the existing Root Setup identity, owner-bound operation, release placement custody and `UpdateOrdinaryAdmissionLease` for the stable machine. That lease excludes a concurrent machine update. Separately keep the target's ordinary command and pairing admission closed while the target serves retained health and while its policy writer holds the pair. Carry that exact admission boundary through handoff and settlement. Treat the current-authority read and target write as distinct accounts and distinct roles. The current authority identity comes from verified caller scope.

A native registration producer for the retained plan and authenticated stage-specific health are prerequisites. The generic activation writers operate on the ordinary plan and the stable transaction gate rejects their use on this store. The existing retained health service label and transcript readers provide the naming and verification contracts. A production listener, verified job identity and exact v6 registration must all be present before C02 is reachable. An owned fixture can set up a database frame to exercise the storage logic. Its proof type cannot enter native dispatch.

Preserve the existing maintenance cancellation path. Before native activation reaches C02, demonstrate open, applied cancel, durable reopen-pending for the exact saved scope, one verified reopen and fresh admission. An unresolved cancel stays in owner recovery. Check the landed cancellation controls and their integration at dispatch review. A maintenance window operation and the completion operation each keep their own authorization.

## Durable operations

The proposal preserves the existing canonical record codecs. Each machine write uses one private, process/thread-bound store authorization in the existing stable-store transaction dispatcher. One connection holds the exclusive machine storage lease for each synchronous transaction. Store captures use the active transaction's narrow frame loan. Invalidate it on return, and refuse nesting, cross-thread use or another writer. Close the machine connection before asynchronous health, service actions or the separate target pair write.

| Operation | Exact mutation and transaction | Proof required by the owner |
| --- | --- | --- |
| Retain completion | Insert one `retained_setup_completion_intents_v1` row, keyed by account, with ID, revision and canonical `.prepared` bytes. Use one immediate transaction. Compare expected absence and unique ID. | Fresh verified registration/completion scope, exact registered v6 plan and inventory, immutable startup intent and actual recorded startup policy and checkpoint. |
| Begin the policy write | Compare-and-swap that row from `.prepared` to `.writing` in one immediate transaction. Match account, ID, old revision and canonical old bytes. Keep ID and immutable operands, advance revision, require exactly one change. | Fresh completion-purpose proof, exact source pair and a confirmed marker after commit. Successful acknowledgement grants one in-memory use tied to that marker, peer scope, process and operation. |
| Commit the policy floor | Close the machine writer, then use the private target Authority journal/continuity writer under the pair's exclusive custody. Consume the acknowledged marker once, re-derive the exact completion policy and use the existing checkpointed write. Return the observed source and result. | Match the actual startup policy, policy and role revisions, journal epoch and head, and continuity checkpoint. Enforce the retained-only journal mode. Acquire the pair without a competing normal Authority writer. Settle the health and pair ownership transition within the same verified attempt, subject to the live lease check in #725. |
| Record completion | Open a fresh machine connection and compare-and-swap `.writing` to `.recorded` in one immediate transaction. Store exact committed policy and checkpoint. The completed floor and checkpoint must satisfy the existing record checks. |

Use a bounded row count and the existing codec size limits. Compare an exact existing row after validating the same frame. A matching durable result is readback. Refuse unrelated rows, conflicting IDs or replacement of a historical readiness verdict. If future requirements allow a new promotion for an account already carrying a readiness record, specify its exact replacement and archival contract separately before adding an update path.

For readiness, construct the record only from the native client's one-use proof. Use a new challenge with a bounded deadline. Verify the root/account-specific job, code identity and key, and the Transport job, execution UID, code identity and key. Bind both peers to the exact candidate, activation, inventory, recorded policy and checkpoint and published promotion. The Transport reply binds to the Authority challenge. The Authority signs the resulting joint transcript. A stored v1 record proves that exchange happened. Require current health again at any later admission boundary. Keep keys, raw transcripts and account identifiers out of shared diagnostics.

## Schema 29 and compatibility

A machine that has run retained maintenance can already have schema 29 with the completion, promotion and readiness tables present and empty. On 29 all three producers modify data in their own existing table. Preserve `user_version`, the window table and every window row, the full catalog, and unrelated rows byte-for-byte. An earlier window provides no writer authority for these operations. Verify the exact settled maintenance state and reject conflicting active or unresolved work.

Audit schema gates at each level. This includes the format requirements and proposal factories, stable and catalog capture, snapshot retention and transition comparators, native scope, private authorization and primitive, and the transaction dispatcher. The reader-side acceptance of 29 does not establish a writer contract. Keep ordinary account, inventory, update and window writer guards narrow. Include catalog and protected-row comparison even when schema stays constant.

Preserve the planned historical first-row transitions if the corresponding paths ship. A completion insert on 25 may create just its table and index and move to 26, a promotion insert on 26 to 27, and a readiness insert on 27 to 28. Put the DDL, first row and version change in the same immediate transaction. Require the declared migration and exact before/after catalog delta. Adjacent phase changes stay on the current schema. On 29 missing tables, unexpected schema, or format/role mismatches fail before mutation. Keep 28→29 under the existing window owner.

Update signed manifest assertions together with each reachable path. Require Authority and Setup readers for the actual schema and records carried by the installation. Declare machine table writers on Setup and journal policy authority on the role that performs that write. Reconcile the current promotion proposal's legacy role/version lists with that concrete producer matrix. Add older writes or migrations only for reachable, qualified producer paths. Check required declarations and compatible reader floors before opening the write transaction.

## Rechecks at each boundary

1. Resolve the peer UID, current authority, target owner, directory identity and installed code from native evidence. Verify candidate signatures, placement, the stable seal and admission boundary. Pin the activation plan, inventory, registered job identities, exact source or promoted files, and both sides of the relevant pair. Acquire scoped custody and prove the same frame again.
2. Perform asynchronous health with the machine connection closed. Bind the answer to the live peer incarnation and attempt. Reacquire the writer, compare a fresh frame with the challenge frame, and check freshness, custody and admission immediately before use. Close and settle the actual connection and jobs as the owner requires. A disconnected, expired, cancelled or counterparty-changed session cannot mint a permit.
3. Under `BEGIN IMMEDIATE`, reread the actual selected row and the protected digest. Recheck target, policy pair under its owned fence, scope and phase inside the transaction before SQL. After mutation verify only the exact expected row and, for a declared migration, the expected catalog delta. Recapture the protected frame just before commit. An in-transaction verifier borrows the transaction frame and uses synchronous, non-mutating checks. It cannot open another machine store or run a service operation.
4. Authorizing the separate journal write needs the committed marker, verified again before the pair mutation, in the journal transaction and after it using the closed-machine marker check. Pin the target pair identity and own both stores until a conclusive receipt or retirement. Use the existing lock order and nonblocking lease acquisition. A busy pair produces the existing refusal. Confirm whether the native health job can hand off the pair while preserving the live peer fence. If the current job cannot lend or release the pair safely, resolve the owner transition before enabling dispatch. A cached reply cannot extend the lifetime of that proof.
5. Read back after commit under the same live owner and compare actual durable bytes; recheck peer and admission before returning a success or permit. In promotion and readiness, bracket external work with fresh reads. Check the same file identity and bytes before and after replacement/readback, and check the publication row again at readiness insertion. A stale sample, late rights change or unknown job state fails closed.
6. Keep the machine frame cache scoped to a single connection and transaction. #960 uses the real registered fixture from C02, commits on a second connection between the two reads of `readFresh`, verifies that commit, and expects `staleRevision` on the second read.

## Interrupted execution

| Last established state | Restart behavior |
| --- | --- |
| No committed machine transaction | Roll back rows, catalog and version together. Resume from a fresh verified frame. |
| Exact committed `.prepared` | Read it back in a fresh scope. Revalidate all operands before starting the next transaction. |
| `.writing` with uncertain acknowledgement or lost permit | Retire the writer and its loans. A fresh owner classifies the actual pair. An unchanged pair with a higher proposed floor leaves the marker unresolved for explicit owner intervention. A changed or partially settled pair stays unavailable until reconciled. No regenerated permit for that marker. |
| `.writing` with proven exact target pair | Validate the existing record's checkpoint, generations, role revisions, digests and unchanged journal head. Record the result with one exact machine CAS. The equal-policy case can record the unchanged exact scope as a no-op receipt. |
| `.recorded` or file promotion interrupted | Verify the actual recorded pair and the same publication intent. Treat already-selected bytes as completed work. Stop on foreign bytes or an uncertain file identity. |
| Readiness commit outcome uncertain | Close the writer and read the actual row in a fresh scope. Return only the exact existing historical result after proof checks. If absent, repeat the read-only native exchange with a new challenge and recheck before a new insert. Fresh health and the separate owner govern any later reopening. |

Use the store's existing poisoned-connection behavior for unknown COMMIT, failed rollback, corrupt records and late custody loss. A definite pre-transaction refusal must leave a valid connection available where the transaction contract permits it. Preserve the primary error through cleanup. The owner releases its leases after actual close or join.

## Proposed PR order and validation

1. Verify or land the retained v6 activation/registration and per-role native proof prerequisites as focused PRs. Use the existing retained maintenance cancel/reopen controls as the compatibility baseline. Establish the exact typed entry and distinguish owned test scopes from native claims.
2. Completion store and permit. Implement schema 29 plus reviewed legacy boundaries, protected frame comparison, exact CAS, and transaction failure retirement. Land the completion owner and journal floor path separately if required. Enable Setup dispatch and writer declarations with the full native path.
3. Use the real completion fixture for #960. In parallel review promotion's schema 29 gates. Publish the promotion changes after the preceding dependency merges, with actual schema 29 retain and phase transitions.
4. Readiness storage and native joint proof. Split the native health work if needed, then wire only the full verified path. The final integration gate exercises the installed registered pair from completion through promotion and readiness.

Owned test coverage per slice includes actual schema 29 database writes on an empty and populated 29 catalog. Check the declared legacy migrations, schema and row digest preservation, missing or corrupt declarations before BEGIN, duplicate and stale CAS, separate-connection drift and writer exclusions. Inject failures before BEGIN, inside the body, before COMMIT, during COMMIT, after commit and between all durable phases. Check the actual persisted rows, lease retirement, fresh reopen and result classification. Exercise the checkpointed journal with exact-source, equal-policy, conclusive target, partial and unrelated changes. Assert one permit use, zero duplicate policy commits and zero admission release at interruption points.

Native proof contract tests cover wrong role, caller or peer incarnation, unavailable services, wrong code or job, expired challenge, unrelated promotion, stale pair, valid but replayed signatures, loss during commit, and close or cancellation before lease release. Use the existing scoped ATC workflow for focused and full gates with Toni's approved test selection and budget. Separately verify live Root and Transport jobs and signing, the busy case from #725, actual installed pair mutation, and restart/readiness on the owner-approved Mac. Record claimable outcomes with the source and artifact identity. This document records source review only.
