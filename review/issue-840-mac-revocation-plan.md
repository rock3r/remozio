# Issue #840 · Revoke a phone from the Mac

This is the second PR in the pairing lifecycle. It depends on the reserved revocation capacity in [#882](https://github.com/rock3r/remozio/pull/882). The Mac owner can remove the exact enrollment of a lost or retired phone without access to that phone. Shared re-pair, Android self-removal, renewal and the biometric migration follow separately.

## Mac owner flow

- Put **Paired phones…** alongside **Pair a phone…** in the main window. Load active enrollments for the current Mac and account from the local Authority. Use a retained display label only if the data already has one. Otherwise show a short identifier from the phone identity and disambiguate collisions. Never show keys, full identifiers or notification tags. Discovery candidates in the pairing sheet are a separate list.
- Use a labeled **Revoke…** action for each row. The confirmation identifies the selected phone and explains that the phone loses access to this Mac and needs pairing to regain it. The OS administrator prompt follows confirmation. Use the default focus for Cancel, support keyboard navigation, and announce success or error via the accessibility status. Localize the labels, confirmation and errors.
- Bind the action to the complete identity and enrolled epoch shown by that snapshot. Disable another submission until this operation returns or its outcome is read back. After a stale revision, show a fresh list and require another explicit confirmation. After a lost response, query the exact old enrollment within the same Mac and account. Cross-account, ambiguous and unavailable outcomes remain distinguishable. If the old epoch is still active after a fresh read, the user can choose a new confirmation and prompt. A missing row or a newly paired epoch alone cannot serve as success evidence.
- Report local success after the Authority confirms the durable checkpoint. With a configured gateway, show a separate pending or confirmed delivery state. The owner can leave the sheet while delivery is pending. A failed read or unverified result stays visible and can be refreshed.

## Local application channel and write owner

Use an optional, independently negotiated management capability on the existing signed local App-to-Root XPC channel. Preserve the existing pairing handshake and network protocol. Old apps continue to pair. New apps suppress the action on older roots. Use a fixed version and bounded, strict canonical encoding with an explicit byte cap based on at most 1,024 retained rows. Decode only the expected shapes, element lengths and unique row identities. Expose a read-only snapshot of active identities and exact epochs, the scope and trust revision, plus a bounded outcome query. Neither endpoint accepts display names as authority. Reject unknown, duplicate, truncated and trailing fields.

Reuse the caller guard of `AuthorityPairingXPCEndpoint` and its retained app role/binding check. Enforce the exact current signed app, expected user, operation budget and existing maintenance admission. The mutation also needs app-supplied OS administrator authorization, validated for the same invocation at entry and rechecked in the durable transaction. Capture the snapshot scope, expected trust revision, phone ID and enrollment epoch. Reject changed scope or revision before any side effect. The first explicit confirmation authorizes exactly the captured enrollment.

Route the write through the existing serialized pairing request owner in `AuthorityJournal` and the checkpointed writer in `ApprovalRequestCoordinator`. Use `JournalDatabase.revokeApprovalEnrollment` with the current audit writer, expected head, and Root-owned event ID. It updates the exact enrollment, trust revision, audit record and any signed gateway control atomically. Resolve gateway registration, signer and expected control head from protected state inside the owner boundary. A configured gateway without valid signing state fails the transaction. Gateway network availability is independent of that signing state. After commit, return success only when the independent continuity check confirms it. On a failed/unknown reply, read the retained revoked record for that exact epoch through the same authenticated, checkpointed channel. A duplicate or stale request cannot write a second removal event or touch a replacement epoch.

## Existing sessions and queued work

Every Root operation that reads or acts for a phone continues to check the committed trust revision and exact peer binding. Review the normal request, pending discovery, decision, audit, routing and push paths. `DirectApprovalTransportService` already revalidates before and after its Authority calls. Check the final byte publication and asynchronous callbacks as well. Use the existing owner for any missing recheck or invalidation. The enforcement boundary is the final live authorization before a new action or response publication. Bytes already handed to the transport and decisions already durably accepted cannot be recalled. A response paused before its final authorization must fail once revocation commits. Never use a cached connection or successful handshake as authority for a new operation.

The authenticated trust feed replaces the listener generation and invalidates stale sessions. Use it for connection retirement, with immediate Root-side refusal after the commit. Ordinary feed latency may delay physical disconnection. Reconcile pending recipients and wake work for the removed epoch using existing trust-driven reconciliation. Keep other active phones eligible. Previous terminal decisions keep their normal outcome. Include LAN and relay through their actual service paths.

## Gateway delivery and recovery

Reuse the authenticated `GatewayRootChannel` recipient operation for `.phoneRevocation`. Add the missing Root client path alongside `applyTokenActivation`, retaining protocol and envelope formats. The gateway already checks exact phone/epoch, registration, signature, revision and expiry. Its delivery owner removes the mapping and cancels wakes for the exact epoch. Keep retry, key custody and reconciliation in the existing Root gateway owner. The Mac app never signs or sends control traffic.

Use the retained control as the authority for post-commit delivery, even when the app closes. Give the gateway owner bounded discovery of unconfirmed controls from the protected journal on startup and after new commits. Keep one active send for the registration. Prefer a still-current envelope with a bounded retry budget. Verify any echoed receipt against the exact sent envelope, then use the existing signed head and paged history query to confirm that the exact revocation was applied. A head beyond its revision by itself is insufficient. Observe every step against the pinned registration and current lifecycle. Replaying an already applied control must preserve its original receipt and must not disturb another epoch.

An unapplied envelope can become unusable at restart, after expiry, or once a later revision is applied remotely. First check for durable gateway evidence. If absent, the protected owner may sign a fresh, bounded delivery control for the same *retained revoked epoch* through the existing writer, with a new operation ID, the current head and the normal signature and time bounds. Preserve the old evidence and do not add a second enrollment-removal event. A newer live epoch cannot be used for the replay. Keep local refusal in force if the ordinary history budget is exhausted, registration changed, or the gateway is unavailable or full. Surface the pending or blocked delivery outcome without treating it as remote success. Never evict retained evidence or bypass the gateway's admission policy. Confirm the existing receiver capacity behavior under a full gateway journal before implementation scope is fixed. If it can permanently prevent delivery for a lost phone, bring the lead the exact capacity dependency before calling the feature remotely complete.
