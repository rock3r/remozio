# Shared re-pair 3b plan

[Issue #840 plan request](https://github.com/rock3r/remozio/issues/840#issuecomment-7095643580) · [Part 3a](https://github.com/rock3r/remozio/pull/899)

Source reviewed at part 3a commit `251a3d065d22a65a90d9f7f8282e80eb7f0ccb54`. Part 3a verifies a revoked predecessor at staging and at the checkpointed commit. The phone currently builds an ordinary proposal before saving an enrollment. Its PREPARED record requires the returned transcript, and its replacement path assumes that the predecessor is locally active. This document proposes changes for review. The baseline observations below are source findings and proposed test witnesses.

## Select the revoked predecessor

- In Mac Setup, let the owner choose an exact retained revoked phone and export a re-pair invitation. Root reads the row under the current local app and administrator checks. It refuses a missing, active, restricted, or stale selection and any active sibling for the same phone ID. Gateway delivery may still be pending after local revocation.
- Keep the ordinary invitation bytes and existing setup exchange. Add a bounded, versioned re-pair envelope for QR and text import. Root signs its canonical invitation and the predecessor tuple of Mac ID, account ID, phone ID, and old epoch under a dedicated signing domain, with a short expiry. The endpoint accepts a typed local selection and constructs the signed bytes itself. It does not sign app-supplied bytes or expose a network lookup for revoked phones.
- The phone verifies the signature and both invitation pins against the exact retained local row before offering **Re-pair**. That row may still be locally active or already marked REMOVED. A local removal, TLS refusal, or gateway status cannot establish Mac revocation. A missing row or mismatched pin leaves only the ordinary pairing flow with a new phone ID. A phone-wide trust restriction remains a refusal.
- The Mac re-pair sheet identifies the selected phone with its existing identifier display. It shows that the verified transcript replaces the old epoch before confirmation. During this session the Mac rejects a proposal for a different predecessor or an ordinary proposal. Keep part 3a's checks at staging and commit, administrator consent, and comparison code on both devices. Neither an invitation nor the sheet grants enrollment.

## Persist before sending the version 2 proposal

1. Match one local record ID and revision against the verified predecessor. Keep its phone ID. Allocate a new record ID, epoch, and three hardware key references. Never copy the old relay credential or key material.
2. Save a PREPARED re-pair entry to the encrypted archive before the channel can write the proposal. It holds the verified invitation, exact predecessor record ID and identity, canonical proposal, and key references. Represent this pre-transcript state explicitly. Keep it out of the active inventory, routing, biometric signer, and receipt lookup until each next checkpoint is present. Keep existing archive readers for ordinary rows. A reader that cannot parse the new pending format must refuse the archive without replacing it.
3. On the same connection, verify the returned transcript against the retained proposal, invitation pins, predecessor, and negotiated policy. Save the exact transcript onto the same PREPARED entry. Then display the comparison and obtain a fresh hardware proof only after confirmation. Persist a proof-may-have-been-sent marker before the first proof write. Failure to confirm a durable write stops network output. A provider error during key creation may clean up only unreferenced keys allocated by this attempt.
4. After restart, a PREPARED entry with no possible proof submission can be cancelled and its unused new keys retired. A fresh explicit attempt uses new keys. Once proof might have been sent, resume only the receipt lookup for the saved setup ID and digest. Authenticate with the new retained transport key. Missing, ambiguous, or mismatched receipts leave the entry and keys intact. Never resend the pairing proposal or proof as part of receipt recovery. Invitation expiry ends new setup and does not discard an outstanding receipt recovery.

## Activate and retire locally

Verify the authority's commit receipt for the exact saved transcript. Under one archive revision check, confirm that the new PREPARED entry and the recorded predecessor still match, and that there is no unrelated active row in the same Mac/account scope. Atomically activate the new row and retire only the recorded predecessor. Accept an already-REMOVED predecessor only if its retained identity still matches. A stale selection or conflicting row leaves the archive unchanged. A repeat after successful activation returns the current result without applying the mutation twice.

After the archive commit, invalidate the affected enrollment owners and retire unreferenced predecessor aliases. Reconcile from the archive if cleanup is interrupted. Leave unrelated records, runtime owners, and referenced keys alone. Preserve Root's old-epoch evidence and use part 3a's gateway projection. The phone action reads **Remove from this phone**, explains that Mac revocation happens in **Paired phones**, and acts on the selected row ID and revision. It sends no revocation request and creates no eligibility evidence.
