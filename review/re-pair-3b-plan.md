### Why the envelope can remain unsigned

The phone keeps the authority and transport pins from its retained enrollment. An imported envelope must match those pins and the exact local tuple. The pins authenticate the Mac setup channel and the commit receipt, respectively. A changed pin, foreign scope, or unknown tuple fails on the phone.

A modified tuple that happens to match another retained row can put the phone on the wrong setup attempt. The Mac checks the tuple against its independent local selection and refuses the proposal. Root also checks revocation at staging and commit. The user must compare the transcript on both devices, and the phone can activate and retire rows only after verifying the Root receipt for that transcript. A stale or changed envelope can therefore interrupt setup without creating authority or retiring a local row. The initial phone UI can offer the guarded re-pair attempt, while only the Mac's checked setup exchange establishes eligibility to continue. The live setup deadline and transcript checks provide the freshness bound.

## Part 3c · Android persistence, recovery, and retirement

### Preflight and durable setup

1. Offer **Re-pair** only when the imported envelope, both existing pins, and the full predecessor tuple match one retained local enrollment. The row may still be locally active or already marked REMOVED. Local removal and transport failures supply no revocation signal. Refuse an already-superseded predecessor, including when its successful successor was later locally removed. Use the durable successor link, never an ordering comparison of random epoch or record IDs. Refuse a sibling active row or an existing PREPARED successor for the same phone ID. A mismatch stops this attempt. Ordinary pairing remains a separate explicit action that generates a new phone ID.
2. Under the archive owner's revision check, reserve at most one re-pair attempt per Mac ID, across retained account rows, and at most one per exact predecessor. An existing PREPARED for the Mac occupies the slot, including during recovery. A repeated import opens the existing attempt's status or recovery instead of starting it again. Enforce this limit together with the existing archive record bound before allocating hardware keys. Keep the reservation across key allocation and the PREPARED write. If the process dies during allocation, use the retained attempt identity to reconcile only its aliases and release the unsubmitted slot. Keep the phone ID and allocate a fresh record ID, epoch, and three hardware key references. Never copy relay credentials or old keys. Persist a PREPARED re-pair entry in the encrypted archive before the channel writes the canonical version 2 proposal. Retain the chosen predecessor, parsed invitation, exact proposal, and key references. Model the pre-transcript state explicitly and keep it outside active use, signing, and receipt lookup. Preserve legacy ordinary records. A reader that cannot parse the new pending format must refuse it without replacing the archive.
3. Validate the returned transcript against the stored proposal, pins, predecessor, and policy. Save it to the same PREPARED entry before comparison and proof. Persist a proof-may-have-been-sent marker before the first proof write. Failure to confirm a durable write stops network output. Only clean up unreferenced keys owned by the failed attempt.
4. When the Mac refuses the proposal before proof, or the user cancels before possible proof submission, drain and close the candidate transport. Recheck the exact entry under the archive lock, release the slot, and retire only its unreferenced new keys. Apply the same cleanup after restart when the durable marker proves no proof could have been sent. This includes a proposal already sent that received a Mac rejection. A new explicit attempt allocates fresh keys. Once proof might have been sent, recover only the receipt for the saved setup ID and digest over the authenticated new transport binding. Missing, ambiguous, or mismatched receipts preserve PREPARED and its keys. Never replay the setup write or biometric proof. Setup expiry does not discard a receipt lookup. Show the pending attempt and a receipt-recovery action so another import cannot hide an outstanding result or allocate new keys.

### Receipt lookup limitation

The current receipt response contains the setup ID and an optional commit signature. The Android client treats an absent signature as receipt unavailable. A candidate that never enrolled may also fail to open the receipt channel. Neither outcome proves an expired setup never committed. Keep an ambiguous entry in the bounded recovery slot until a verified receipt or the narrow supersession proof below resolves it. An authenticated terminal no-commit response, with durable evidence that the setup cannot commit, would need a separate protocol change.

### Activation and local removal

Verify the Root commit receipt for the exact saved transcript. In one archive write, check the revision, the matching PREPARED entry, the exact predecessor, and the absence of a conflicting active row. Activate the new entry and retire only the pinned predecessor. Record the successor link in the same write as retirement. An already-REMOVED predecessor is eligible only if the retained row still matches and no successor has superseded it. Repeating a successful recovery returns the current result. A stale or changed row leaves the archive unchanged.

In a valid archive the one-attempt guard prevents sibling PREPARED rows. If reconciliation nevertheless encounters a sibling for that exact predecessor, a never-submitted entry can be closed. An ambiguous sibling can be closed as superseded only if the verified winner receipt binds a different setup, epoch, and keys to the same predecessor and the **same expected Root trust revision** as the sibling's retained transcript. Both commits consume that revision in the guarded transaction, so the receipt proves the other commit cannot have succeeded. Perform terminalization in the same archive write. If the revisions differ or the proof is absent, retain the ambiguous entry for receipt recovery. A newer active row, a missing receipt, or a timeout alone cannot prove it never committed.

After the commit, invalidate affected enrollment owners and retire only unreferenced aliases. Reconcile from the archive after interruption. Keep Root's old-epoch evidence and existing gateway projection. Label the local removal action **Remove from this phone** and explain that revocation happens in **Paired phones** on the Mac. Apply removal to the selected record ID and revision, with no revocation request or effect on other rows.
