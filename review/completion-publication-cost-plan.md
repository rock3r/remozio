# Measure and reduce completion publication cost

[Issue #1069](https://github.com/rock3r/remozio/issues/1069) tracks product work. This plan is based on main at `e0b10957`. A seven-entry test completed in 46.671 seconds. Time Profiler attributed 45.892 seconds of weighted CPU samples to its stack. `completionPublicationSnapshot`, `loadCompletionRecoverySnapshot`, `requireInLeases` and `requireEntry` overlapped. Their inclusive times were 44.136, 39.153, 39.360 and 37.021 seconds. The test runs writes, rollback, recovery and replay scenarios. It does not establish the cost of one installed update.

The seven entries are six configuration files and one authority job for one account. The fixture has no Gateway backend capture. It calls the retain helper six times and the file coordinator five times. The sample export contains neither dynamic call counts nor real payload sizes.

## Measure each operation

Add a temporary measurement patch to the existing publication test. Use its production path and existing fixture. Add observer calls for private functions only in the throwaway measurement patch. Remove the patch after the run. Keep the production and review branches free of the measurement code.

- Record entry, exit and outcome for each retain, prepare, complete, file exchange and finalization attempt. Use integer attempt, stage, transaction and scope IDs. Keep the existing write, fault, retry and replay sequence.
- Count actual calls to `completionPublicationSnapshot`, `loadCompletionRecoverySnapshot`, `CompletionPublicationScope.read`, `requireInLeases`, `requireEntry`, and each immutable cache hit or miss. Count entries visited and successful scans separately. An early failure can make a scan shorter than the plan.
- Record monotonic elapsed time and XCTest process CPU for each call. Run one selected test per process. Report counts, totals, per-call mean and median, and per-step totals. Use parent IDs to subtract child intervals from exclusive cost. Keep inclusive times visible and avoid summing overlapping calls.
- At the existing materialization points, count `startup` and `completion` bytes per plan entry. Count the already produced record JSON before SQLite bind, with schema, stage and outcome. Count immutable validation key input bytes and actual file bytes read. Read `Data.count` from existing values and avoid a second encode. Record only lengths and classifications. Keep payloads and file paths out of the report.
- Capture three serial passes of the existing test with the same optimized flags, binary and host configuration. Use an uninstrumented run to estimate probe overhead. Confirm the same rollback results, marker order, idempotent replay, original inode after acknowledgment replay and terminal state. The deadline cap is 900 seconds for the build and 600 seconds per pass.
- Separate entry-count scaling from byte scaling. Use a second admitted account from the existing completion fixture only after both recorded policy boundaries validate. Compare matched plans with the same operation/fault script. Then vary valid canonical operand sizes at a fixed entry count. If a second fixture cannot vary one dimension independently, report the measured sizes and leave scaling unproven.

## Reduce repeated work in separate changes

Start with the operations whose inputs are immutable. Use before and after profiles to choose the next change.

| Candidate | Required check |
| --- | --- |
| Compute plan fingerprints and per-entry startup/completion hashes once on a verified immutable plan. Reuse the derived values in `requirePlan`. | Compare every account, owner, file, source/target inventory digest and entry digest with the current record. Keep the same canonical encoding and digest domains. Still verify actual file bytes and metadata. |
| Reuse the SQLite-only part of the publication frame within one read transaction. Follow the existing stable frame cache rules. Skip an immediate second full frame load before the first borrower callback only after showing no intervening effects. | Require the active connection, read transaction state, transaction serial, unchanged `total_changes64`, the exact candidate and publication ID/revision, and the bound plan. Recheck the restart lease, destination identity and machine boundary on every read. Recapture every external compatibility input, including shared-import state. Expire the loan on any error or change. |
| Avoid reopening the same bound directory during redundant validation when the operation can retain its directory lease. Reuse only the directory handle and immutable plan data. | Validate the directory again against current path and identity. Require current owner, mode, type, link count and exact startup/completion bytes. Keep stage, process and thread ownership checks. An open file descriptor alone does not prove the current path still names that file. |
| Merge two full-file scans only within a proven effect-free interval on the same publication revision. A candidate is the pair around the built-in no-op store notification. An injected notification keeps two scans. | Keep full validation across callbacks that can change a sibling, every write/commit boundary, and each return to a caller. Keep the selected entry verification before exchange, the exact-byte/path/metadata checks at exchange, and readback after exchange. If a live check or callback can change state between the candidate scans, retain both. |

Reuse of database-derived state is limited to one read transaction. Clear it on begin, commit, rollback, shutdown, write upgrade or a changed key. Misses use the full path. Keep full loads in the before-transaction, in-transaction, after-mutation and after-commit scopes when they belong to different transactions or a write transaction. A drain blocks cooperating admission. It does not establish that disk, another journal, or the caller's callback stayed unchanged.

Do not replace `CompletionPublicationScope.read()` with a cached return. Keep process/thread checks, the active transaction and scope checks, and revocation on failed verification. Leave the nested verification around borrowed file and store callbacks in place. Keep the durable writing marker before file exchange, the acknowledgment after readback and replay of a completed exchange after a lost acknowledgment.

## Use fixed-size validation cache keys

For configuration and backend pure validation, derive a 32-byte SHA-256 index from the existing domain-separated, length-framed input. Stream the parts, so creating the key avoids building a large concatenated `Data`. Include the canonical record and each artifact's kind, account and actual bytes in order. Include the exact configuration key in the backend key. Keep a versioned domain for each computation. Never use a declared digest or revision as a substitute for hashing the actual inputs.

Keep the current byte-equality guarantee on a digest hit. Store a bounded reference to the validated immutable inputs behind the fixed-size index and compare the exact framed inputs. A digest collision is a miss. A repeated lookup may reuse an already computed digest only for the same immutable archive inputs. A new read validates its exact inputs again. If the digest and equality check cost more than the current path, retain the current path and report the comparison.

Keep insertion after successful pure validation, store ownership, the PID guard before locking, synchronization, eviction and both entry and retained-byte limits. Do not share a cache across stores, processes or mutable records. The initial change covers the two archive validation caches. The exact-byte value/decode caches and installed-release key path stay outside the first change.

## Design after measurement 1b

The first changes can reduce the cost of a load without changing when verification runs. Keep file scans as they are. The single seven-entry fixture measured 4,782 recovery loads and 177 scans. The native helper defines a full scan, but no production caller invokes that coordinator today. Future integration must keep the total number of entry visits linear, even when full scan calls grow linearly.

### Current configuration epoch

`PreparationIntentStore.requireCurrentConfigurationEpoch` proves that a retained configuration archive still matches the current machine. It checks machine identity and the destination. It loads the schema, configuration epoch, activation, restart source and, when the schema calls for it, the backend epoch. It recomputes source digests under the expected schema labels and compares current installation, admission, account count and per-account source digests. The caller binds the result to the restart lease and its machine boundary.

- **SQLite inputs.** Schema and row state can change after a writer commits. The activation, inventory, candidate, admission, configuration and backend headers, ordered artifact rows, provisioning history and account/runtime rows come from the current connection. A stored revision cannot establish that the underlying bytes still match.
- **Pure values.** Canonical encodings, artifact comparisons and account digests are deterministic given their exact input bytes. Compute each account's digest once on the immutable source within the current load. Reuse the pure result for the same immutable source and account. Keep identity, row membership and equality comparisons at each original check. Bind any memo to exact inputs, including the presence or absence of each field.
- **Optional transaction reuse.** First separate the SQLite-only source reconstruction from external captures and live destination checks. Reuse only the SQLite part, in one read transaction on this store and connection. Match the transaction serial, `sqlite3_total_changes64`, exact candidate key, expected epoch bytes, effective schema, and source-digest schema where relevant. Require an active store, autocommit off, `sqlite3_txn_state(db, "main") == SQLITE_TXN_READ`, no write flag, and unchanged connection identity. Clear on begin, exit, close, rollback or write. If a layer cannot prove that every input comes from that read snapshot, keep its original live read.
- **Freshness.** Follow the existing stable frame cache premise. A read transaction in the store's rollback journal mode holds the SQLite shared lock while it reads. An external SQLite writer cannot commit a changed view inside that read transaction. The transaction serial separates committed snapshots; the changes counter catches own row changes, and transaction mode rejects upgrades including schema-only writes. `data_version` can help diagnose another connection's commit. It does not cover own-connection writes or external files. Revalidate the current machine/destination identity and admission on every use. Recapture every shared-import journal and relay input using the original lease or borrow. Compare their current external digests before allowing reuse. A change or failed capture takes the original path or throws as appropriate. [SQLite data version](https://sqlite.org/pragma.html#pragma_data_version), [SQLite total changes](https://sqlite.org/c3ref/total_changes.html)
- **Estimate.** Load-scoped Time Profiler samples give 18.735 s inclusive for the function, about 3.92 ms per observed load across the 4,782 call denominator. Its restart-source reconstruction accounts for 13.130 s, about 2.75 ms per load. This bounds a candidate improvement and includes work that must stay fresh. For an initial forecast, recovering half of that portion on eligible hits gives about 1.37 ms per hit. If half the loads are eligible, the case average saves about 0.69 ms per load. Both fractions need measurement. No current trace shows read/write eligibility or exact reusable cost.
- **Tests.** Demonstrate one verified SQLite-only reconstruction in one read transaction. Have another connection attempt a known-valid commit during the read, then commit between two reads. The latter read must use the changed frame or reject it. Test own-connection row and schema writes, different candidates and epochs, reopened paths, shared-import and relay mutation within the same SQLite read, and a failed recapture. Cover the exact candidate with the existing stale-snapshot and foreign-fixture checks. Every write path still loads live facts before, inside and after its mutation.

### Completion intent archive snapshot validation

`MachineUpdateCompletionIntentArchive.requireSnapshot` checks a loaded archive against a freshly verified restart snapshot and source digest. It validates the intent header and ordered policy rows. The record compares its expected activation, epoch scope, accounts, inventory and target release with the snapshot. Each policy checks its corresponding source policy, completion binding and archived operands. Both the record and each policy construct `MachineUpdateRestartHealthPlan` for the same snapshot and candidate.

- **SQLite and external inputs.** The intent and policy rows arrive from SQLite and can change on a new read. The snapshot contains current rows and freshly captured compatibility inputs. The caller must still acquire and validate them. The caller's `currentSourceDigest` comes from the fresh machine check and must equal the archived digest. Record or candidate identity alone cannot validate a changed source, policy or target inventory.
- **Pure values.** `Archive.validate` reads only canonical header and ordered policy bytes. Its successful result can use exact-byte equality, with the same domain and length framing. The health plan validates immutable snapshot and candidate values. Reuse its successful result once per archive call for the identical already captured snapshot and candidate. Keep the record and policy validation order, both standalone entry points, all comparisons with the current source, and the same errors. A private per-call result is sufficient for this change. It needs no new cache shared across transactions.
- **Limits.** Do not memoize `requireSnapshot` as a whole or cache a positive freshness result. Keep the policy/journal owner checks at the same boundaries. If a future pure memo crosses calls, bind it to the exact ordered intent and policy encodings, configuration and backend headers and artifacts, canonical restart operands, and the canonical candidate manifest with its role/dependency hashes. A changed byte gives a miss. Keep the source digest comparison and all live reads outside the memo.
- **Estimate.** The archive accounts for 15.272 s inclusive, about 3.19 ms per observed load. Load-scoped samples put 7.238 s in the record's health plan and 6.698 s in the policy's duplicate health plan. Sharing one successful plan per call gives an upper estimate of 1.40 ms per load for this one-policy fixture. Forecast 1.0–1.4 ms net savings for that isolated change, pending before/after tests. The 113 ms inside archive-only validation is about 0.024 ms per load and is a lower priority.
- **Tests.** Compare both standalone checks and the combined archive path on the valid fixture. Mutate a policy row, source account, target inventory, candidate hash or source digest between reads while preserving earlier inputs where possible. The next validation must refuse or compute from new bytes. A failed plan or policy check must never be reused. Keep the existing completion intent rollback, stale-snapshot, foreign-policy and lost-acknowledgment coverage. Add a test-only count of health-plan builds to show one valid build per archive call.

### Proposed first validation

Measure the per-call health-plan reuse first. It has a measured duplicate and needs no freshness-cache change. Compare three serial runs of the same publication fixture with a test-only health-plan count and exact error outcomes. Follow with the completion intent and publication selectors in `MachineUpdateReplacementTests` and the full eight-shard Core gate before publication.
